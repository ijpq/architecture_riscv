## 展开与软件流水解决的不是同一件事

展开将多次迭代显式复制到更大调度范围，让独立 load/算术交错，并减少分支开销。软件流水把不同迭代的 load、计算、store 放在同一稳态周期组中；它还需要填充和排空。只画稳态 kernel 不能证明有限长度循环正确。

先写延迟和启动间隔，再写每迭代所需资源。比如每迭代有两次 load 和一次 store、共享一个每拍接收一次请求的端口，稳态 initiation interval 至少为 3 拍；这只是资源下界，真依赖和控制可能进一步限制。

无 interlock 的题目中，提前读一个未就绪结果不会自动停下来帮你纠正。因此“调度更短”必须先满足每条依赖的可用时刻；NOP 有时是正确性需要。

## trace scheduling 要同时维护所有路径

热路径可以从 profile/概率挑选，但非热路径仍须保持程序含义。跨分支提前执行纯计算，比提前不可逆写内存或可能引发异常的 load 更容易安全处理。IA-64 的 predicate、推测 load、检查/修复，是为这类限制提供的机制，不能假设普通 RISC-V 指令已经自带这些语义。

第 18、27 页的兼容/变延迟问题说明静态安排依赖实现假设。VLIW 仍可适合可预测、专用环境；历史通用产品结局不能替代逐项成本分析。

## 基础自检（约 10–15 分钟）

1. 规定 load 在发射后第 3 拍可用、加法依赖它，且无 interlock。load 在第 0 拍发射，add 最早何时能用该值？把可用时刻写在图上。
2. 每迭代 2 load+1 store，只有一个每拍接收一个访存的端口。为什么“每拍启动一迭代”不可行？
3. 软件流水图中标出 `load(i+1)、add(i)、store(i−1)`。循环第一次进入时为什么不能直接执行这整个稳态组？

<details>
<summary>完成后核对要点</summary>

1. 第 3 拍或之后，本题已明确使用边界；不同题目的“3-cycle latency”需核对写读约定。
2. 平均每迭代需 3 个端口拍，资源下界 II≥3；加功能单元未必解决访存端口瓶颈。
3. 早期没有已经计算好的 i−1 结果，需 prologue；最后还需 epilogue 排空未存结果。

## 补缺／迁移（选做，实践后）

1. 优化前每迭代 5 拍，优化后稳态 2 拍、固定启动/排空共 12 拍。忽略其他开销，哪些 N 才严格更快？为什么报告不能只给峰值 FLOP/cycle？
2. 热路径上提前执行一个可能越界的 load，非热路径原本根本不会执行它。解释仅添加“结果不用就丢掉”为什么不足以保证语义。

<details>
<summary>检查方向</summary>

比较 `5N` 与 `12+2N`，N>4 才严格改善。错误路径上的异常/访问副作用也需控制；需要合法移动条件、延迟异常检查或其他明确机制。

</details>
