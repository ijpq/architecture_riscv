## 同一拍仍有程序顺序

假设两条同拍重命名：`add x4,x1,x2`、`sub x5,x4,x3`。第二条不能仅从拍初旧映射读取 x4；它要使用第一条刚分配的新物理目的。硬件需要组内依赖比较/映射旁路，更多表端口本身不解决这个问题。

## store 与 load 为什么特殊

寄存器依赖在 decode 看到名字即可判断；访存依赖要看最终字节范围。推测 store 可先算地址、数据并写入临时队列，但在可提交前不能不可逆修改内存。提交之后也可能先留在已提交缓冲中，稍后才排空到 cache。

load 若与多个较老 store 匹配，应选**程序顺序上最近、且比自己老的那条**。不能让一个比 load 更年轻的 store 因更早算完就转发给它。地址已知但 store 数据未就绪时，也不能直接使用 cache 中旧数据。

保守方案等所有较老 store 地址已知且不重叠再让 load 越过；地址推测允许先猜无依赖，同时保留检测信息。后来发现重叠，必须 squash/replay 受影响的 load 及相应年轻工作。推测性 load 的异常也要留到正确提交位置处理。

## 基础自检（约 10–15 分钟）

1. x4 原来映射 P4，前述 add 分配 P9，同拍 sub 的 x4 源应使用哪个物理寄存器？为什么？
2. 程序依次是 `store X=1; store X=2; load X; store X=3`。假设有关 store 数据已准备，load 可从哪次写转发？即使最后一条先执行呢？
3. load 越过未知地址的较老 store 执行，后来发现两者访问同一字。怎样恢复？只改 load 的目的寄存器够吗？

## 补缺／迁移（选做，实践后）

1. 较老 store 写 `[0x1000,0x1003]` 四个字节，年轻 halfword load 从 `0x1002` 读两个字节。为什么“起始地址不同”不能证明独立？
2. 两个程序中，load/store 分别总不别名、经常别名。比较“永远等待”“永远猜无依赖”“按历史预测”的预期行为，并设计可验证的短序列。
